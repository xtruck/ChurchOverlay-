# Roadmap

This file exists so deferred ideas have somewhere to go besides the v1 codebase.
See `ARCHITECTURE.md` section 3 for the authoritative out-of-scope list, section 50 for the extension seams each item slots into, and section 59 for the Phase 2 scope-change record below.

## v1 (current)

Core pipeline only: mic → cloud ASR (Deepgram streaming primary, Groq failover; see `ARCHITECTURE.md` section 95) → regex verse detection → hallucination-guarded lookup → OBS overlay. See `ARCHITECTURE.md` for the full spec.

## Phase 2 (approved — scope change recorded in ARCHITECTURE.md section 59)

Audience shift: ChurchOverlay is no longer scoped as one specific church's internal tool — it's meant to be installable by other churches. It stays a local, single-install Electron desktop app (no hosting, no multi-tenant backend); "installable by other churches" means generic branding (a church name/branding step in first-run setup) and no church-specific defaults left in the app, not a hosted product. **Implemented** — architecture note in `ARCHITECTURE.md` section 92: an optional organization name and accent color, set at first-run setup, applied to the operator dashboard's own header/branding (never the congregation-facing overlay, and never a church-specific default baked into the app).

Visual refactor of the existing v1 screens (dashboard, overlay, setup screen) is approved as a single full pass first — cosmetic only, no scope or interface changes, no architecture-review requirement of its own (ARCHITECTURE.md section 57 item 4).

Build order below, by risk, dependency, and real-world urgency — each still needs its own dedicated architecture note before its code starts (ARCHITECTURE.md section 59.3). Voice-driven verse navigation, NDI output, and bilingual display/French localization were all added mid-session as extensions beyond the original three Phase 2 items:

1. **Bilingual display & French localization** — implemented; architecture note in `ARCHITECTURE.md` section 63. The app supports English-only, French-only, and bilingual display (French primary), setup persistence, live dashboard/voice switching, and English/French UI localization. Offline French fallback is documented in section 77. Sequenced first: the app's actual, confirmed target for its first real deployment is a French-speaking church, making this the most urgent item rather than the newest. Verse content can display English-only, French-only, or bilingual (French prioritized/larger, confirmed explicitly) via a `LocalizedVerseSource` wrapping the existing English `FreeApiSource` and a new `GetBibleVerseSource` (Louis Segond 1910, verified live against `api.getbible.net` — a real, free, no-key API, not assumed) — needs no new WS action or protocol change at all, since `Verse` just gains an optional `secondary` field (section 63.3). Mode is both a setup-time default and a live dashboard toggle (confirmed explicitly), via IPC, not WS. Separately, the operator dashboard and setup screen's own interface text gets a full French translation with a language switch (confirmed explicitly — not just verse-content settings) via a small dependency-free `data-i18n` lookup mechanism (section 63.5) — a large, mechanical translation effort sized as its own implementation slice.
2. **Media library** — architecture note complete (`ARCHITECTURE.md` sections 60 and 84), server-side and dashboard UI implemented; Electron file-picker wiring and the media-grid dashboard UI are both done. Song lyrics, originally planned alongside this, is dropped from Phase 2 entirely (confirmed explicitly) — this is images/video/audio only. v1 of this feature supports full playback transport (play/pause/seek) for video/audio, voice-triggered media by exact title match, principal image pinning, and optional per-cue auto-clear timers.
3. **Voice-driven verse navigation** — implemented; architecture note in `ARCHITECTURE.md` section 61. Fixed-synonym commands, boundary rollover, elliptical references, display-mode switching, and hallucination-guard validation are wired and tested. Mic start/stop by voice remains excluded. An extension of the already-shipped verse pipeline rather than a new domain, raised mid-session and scoped separately from the original three items above. Next/previous verse, next/previous chapter, cancel/clear, and jump-to-a-named-book-and-chapter, all by voice, using a small fixed synonym list per command (confirmed explicitly — not exact-phrase-only, not fuzzy/semantic matching) and server-authoritative current-position tracking with `BOOK_CATALOG`-driven boundary rollover. Every computed reference still passes through `KnownValidVerseIndex.exists()` before display — never bypassed. Does not include mic start/stop by voice (confirmed explicitly excluded).
4. **Service rundown & scenes** — architecture note complete (`ARCHITECTURE.md` section 64), server-side and dashboard UI both implemented. A real new stateful subsystem (verse / media / announcement / blank scenes, stepped through in sequence) with an explicit state machine, not scattered booleans. The precedence question section 59.4 deferred is now resolved: live detection always wins — a live-detected, overridden, or voice-navigated verse always overlays immediately regardless of the rundown's current scene, pausing (not discarding) that scene. Control returns to the paused scene automatically when the interrupting verse is cleared; an explicit operator rundown action (`scene:next`/`previous`/`goto`) during an interrupt always wins instead and discards the pause. New operator-only WS commands (`rundown:load`, `scene:next`, `scene:previous`, `scene:goto`) and a new `rundown:state` broadcast event. The dashboard's "Service Rundown" card lets an operator build a scene list (button-based reorder/remove, not drag-and-drop — see section 64.5) and step through it live. Cross-restart persistence remains explicitly deferred (section 64.5) — a loaded rundown is in-memory only today.
5. **NDI output** — optional transport implemented (`ARCHITECTURE.md` section 62). It reuses the overlay's existing HTML/CSS/JS in an offscreen Electron window, sends BGRA frames through `@stagetimerio/grandiose`, has a dashboard enable/disable control, and falls back to Browser Source when the native module is unavailable. SDK redistribution terms and a tested packaged Electron proof for supported platforms remain release gates.
6. **Deepgram streaming ASR** — optional provider and on-demand failover implemented (`ARCHITECTURE.md` section 86). Deepgram stays dormant until sustained Groq 429s, and return to Groq is operator-controlled. Provider billing/credits remain external service constraints.
7. **ASR quality tooling** — deterministic post-processing, bounded audio chunking, and offline WER benchmark utilities are implemented (`ARCHITECTURE.md` section 87). Local Whisper was later approved as an opt-in, default-off offline backup — see item 12.
   Bounded final-transcript assembly and operator-selectable responsive/balanced/robust audio profiles are also implemented; both remain deterministic and feed the existing validation pipeline.
8. **AI copilot** — highest risk. The sermon-notes side channel is implemented. A narrow, strictly one-shot post-service summary (architecture note in `ARCHITECTURE.md` section 93) is also now implemented — an operator-triggered digest of already-validated verses shown plus already-generated sermon notes, never a live agent and never a new Bible lookup. A general chat/reference/slide copilot remains deferred until its own separate approval and validation design exists.
9. **Web-research-driven enhancements** — architecture note complete (`ARCHITECTURE.md` section 65), implemented incrementally, subsection by subsection. Elliptical reference continuation ("verse 16" after "Romans chapter 8"), a trigger-source indicator (detected/override/navigation/rundown), an auto-send vs. review-and-approve mode (auto-send stays default), a voice command to switch display mode, an on-demand glossary lookup by voice, a phone-based second-operator remote (reuses the existing operator token), an AI sermon-notes copilot (section 65.7, see above), and post-service transcript/quote-card export.

10. **Streaming-first transcription, mic health, detection precision** — implemented (`ARCHITECTURE.md` sections 95–97): Deepgram streaming primary with Groq failover (both directions), adaptive gain + live mic diagnosis, spoken-reference normalization (ordinals, number words, compact forms).
11. **Verse-by-quotation suggestions** — implemented (`ARCHITECTURE.md` section 98): deterministic LSG 1910 word-run matching, always a pending suggestion, never auto-shown. Not the deferred semantic detector.
12. **Offline whisper.cpp backup** — implemented (`ARCHITECTURE.md` section 99), moved out of "Deferred": downloaded on demand, verified, last link of the fallback chain. Windows x64 only.
13. **Operator console redesign** — implemented (`ARCHITECTURE.md` section 100).

14. **NDI output hardening** — implemented and unit-tested; real-Electron frame probe passes (`ARCHITECTURE.md` section 109). Four defects reproduced in real Electron before any change: 800×600 frames, opaque-white background, premultiplied alpha sent as straight, and no frames while the overlay is idle. Fixes: forced transparent 1920×1080 window, un-premultiply, steady keep-alive cadence, bounded retry with stats. The final hop to a real NDI receiver is not verifiable in the development environment and the section 62.5 licensing/packaging gates remain, so delivery to a receiver is still unproven.
15. **Overlay style system** — implemented (verified in Chromium and against a real AppCore; not yet exercised in the packaged Electron app); **scope change approved by the owner** (`ARCHITECTURE.md` section 110). A bounded slice of the formerly Deferred "branding engine": church logo and name as freely placeable items, grouped colour palettes (plus custom), additional card designs, and a dedicated Overlay settings view applying changes live with no service restart. Still not a general design tool, theme marketplace or plugin system.

16. **Offline faster-whisper backend** — implemented (`ARCHITECTURE.md` section 113): a second, selectable offline engine behind the section 99 chain (cloud stays primary). Windows x64, CPU only; CUDA and real-service accuracy comparison remain open.

17. **AI transcript cleanup** — **scope change approved by the owner in chat (AGENTS.md section 4); architecture note in `ARCHITECTURE.md` section 123.** Optional, default OFF, inert without an Anthropic key. A final transcript that mentions a reference context is also sent (text only) to the model to correct book names, numbers, accents and FR/EN confusions. The corrected text is only a candidate: it goes through `RegexDetector`, `KnownValidVerseIndex` and the verse source like any text, never delays the raw-text path, falls back to the raw text on timeout, and a reference found only in the corrected text is a pending suggestion (`origin: "ai"`), never auto-shown. The original transcript stays the source of truth.
18. **AI semantic verse suggestions** — **scope change approved by the owner in chat; `ARCHITECTURE.md` section 124.** Moves the formerly Deferred "Semantic / paraphrase-aware verse detection" into Phase 2 as an optional, default-OFF, key-gated proposer for paraphrased or loosely quoted passages. Output is ALWAYS a pending suggestion (`origin: "ai"`); every proposed reference is validated through `KnownValidVerseIndex` and fetched via the verse source, with cooldowns and a call budget. Still no vector search and no new Bible database.
19. **Live sermon copilot (operator suggestions)** — **scope change approved by the owner in chat; `ARCHITECTURE.md` section 125.** Optional, default OFF, key-gated. Periodically (~45 s) the recent validated final transcript yields operator-only dashboard suggestions: up to 3 related verses (validated and fetched like any verse) and a key-point caption / slide text. Never shown on the overlay automatically, never a free-form chat agent, no new Bible lookup path.
20. **Post-service extras** — **scope change approved by the owner in chat; `ARCHITECTURE.md` section 126.** Extends the one-shot service summary (section 93) with AI-selected quote cards (chosen only among already-shown verses and verbatim sermon-note lines), a French + English recap, and a notes export (Markdown plus card images). Operator-triggered, needs the Anthropic key, based only on already-validated verses and already-generated notes.

21. **Free AI service (Groq text models)** — **requested by the owner in chat; `ARCHITECTURE.md` section 128.** A second `TextCompleter` next to Anthropic that reuses the Groq transcription key, chosen explicitly (never a silent switch). Implemented; not yet exercised against the live Groq API.
22. **Animated overlay backgrounds** — **scope change requested by the owner in chat; `ARCHITECTURE.md` section 129.** A bounded slice of the overlay style system (item 15): a closed list of procedurally drawn, full-screen-layout-only backdrops. First background, "fire", implemented; candle (prayer), light rays, water and clouds/stars follow one at a time after the first is judged on a real service in OBS. Not a video library, not user-supplied animation.

## Deferred — not v1, do not implement without an explicit architecture review

Each item below is a candidate future milestone, added as a new implementation behind an existing extension seam (`AsrProvider`, `VerseDetector`, `VerseSource`) wherever possible — not a rewrite.

- **Gemini Live + Google ADK as a `ReferenceInterpreter`** — using Gemini Live's full-duplex streaming understanding to propose a Bible reference directly from speech (instead of transcript + regex). Evaluated and explicitly deferred (not rejected outright): requires real session-management engineering (10-minute forced WebSocket reconnects, resumption tokens, 15-minute context cap without compression) that Groq's stateless per-chunk requests don't need. Its own output would still have to pass through the same hallucination-guard pipeline as any other interpreter — an LLM-proposed reference is never trusted directly, per ARCHITECTURE.md §15. If revisited, build it as an additional `ReferenceInterpreter`/`AsrProvider` implementation alongside Groq/RegexDetector, not a replacement. One candidate building block for Phase 2's AI copilot item above, not the whole of it.
- ~~Semantic / paraphrase-aware verse detection~~ — approved by the owner in chat and moved to Phase 2 item 18 above (an optional, key-gated, suggestion-only proposer; `ARCHITECTURE.md` section 124). Vector search stays deferred.
- **Multiple Bible translations, a general offline-first Bible database, vector search** — new `VerseSource` implementations. (A narrow, single-language offline fallback used only for live-API outage resilience — not a general offline database or a new translation — is already implemented; see item 1 above and `ARCHITECTURE.md` section 77.)
- Cameras
- ~~Branding engine~~ — a bounded slice (logo, name, palettes, overlay settings) was approved and moved to Phase 2 item 15 above. A *general* theming/branding platform (themes beyond that slice, per-service look scheduling, template marketplace) stays deferred.
