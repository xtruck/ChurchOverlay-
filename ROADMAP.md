# Roadmap

This file exists so deferred ideas have somewhere to go besides the v1 codebase.
See `ARCHITECTURE.md` section 3 for the authoritative out-of-scope list, section 50 for the extension seams each item slots into, and section 59 for the Phase 2 scope-change record below.

## v1 (current)

Core pipeline only: mic → cloud ASR (Groq) → regex verse detection → hallucination-guarded lookup → OBS overlay. See `ARCHITECTURE.md` for the full spec.

## Phase 2 (approved — scope change recorded in ARCHITECTURE.md section 59)

Audience shift: ChurchOverlay is no longer scoped as one specific church's internal tool — it's meant to be installable by other churches. It stays a local, single-install Electron desktop app (no hosting, no multi-tenant backend); "installable by other churches" means generic branding (a church name/branding step in first-run setup) and no church-specific defaults left in the app, not a hosted product.

Visual refactor of the existing v1 screens (dashboard, overlay, setup screen) is approved as a single full pass first — cosmetic only, no scope or interface changes, no architecture-review requirement of its own (ARCHITECTURE.md section 57 item 4).

Build order below, by risk, dependency, and real-world urgency — each still needs its own dedicated architecture note before its code starts (ARCHITECTURE.md section 59.3). Voice-driven verse navigation, NDI output, and bilingual display/French localization were all added mid-session as extensions beyond the original three Phase 2 items:

1. **Bilingual display & French localization** — implemented; architecture note in `ARCHITECTURE.md` section 63. The app supports English-only, French-only, and bilingual display (French primary), setup persistence, live dashboard/voice switching, and English/French UI localization. Offline French fallback is documented in section 77. Sequenced first: the app's actual, confirmed target for its first real deployment is a French-speaking church, making this the most urgent item rather than the newest. Verse content can display English-only, French-only, or bilingual (French prioritized/larger, confirmed explicitly) via a `LocalizedVerseSource` wrapping the existing English `FreeApiSource` and a new `GetBibleVerseSource` (Louis Segond 1910, verified live against `api.getbible.net` — a real, free, no-key API, not assumed) — needs no new WS action or protocol change at all, since `Verse` just gains an optional `secondary` field (section 63.3). Mode is both a setup-time default and a live dashboard toggle (confirmed explicitly), via IPC, not WS. Separately, the operator dashboard and setup screen's own interface text gets a full French translation with a language switch (confirmed explicitly — not just verse-content settings) via a small dependency-free `data-i18n` lookup mechanism (section 63.5) — a large, mechanical translation effort sized as its own implementation slice.
2. **Media library** — architecture note complete (`ARCHITECTURE.md` section 60), server-side and dashboard UI implemented; Electron file-picker wiring and the media-grid dashboard UI are both done. Song lyrics, originally planned alongside this, is dropped from Phase 2 entirely (confirmed explicitly) — this is images/video/audio only. v1 of this feature supports full playback transport (play/pause/seek) for video/audio and voice-triggered media by exact title match, both confirmed explicitly as genuine architectural decisions, not assumed.
3. **Voice-driven verse navigation** — implemented; architecture note in `ARCHITECTURE.md` section 61. Fixed-synonym commands, boundary rollover, elliptical references, display-mode switching, and hallucination-guard validation are wired and tested. Mic start/stop by voice remains excluded. An extension of the already-shipped verse pipeline rather than a new domain, raised mid-session and scoped separately from the original three items above. Next/previous verse, next/previous chapter, cancel/clear, and jump-to-a-named-book-and-chapter, all by voice, using a small fixed synonym list per command (confirmed explicitly — not exact-phrase-only, not fuzzy/semantic matching) and server-authoritative current-position tracking with `BOOK_CATALOG`-driven boundary rollover. Every computed reference still passes through `KnownValidVerseIndex.exists()` before display — never bypassed. Does not include mic start/stop by voice (confirmed explicitly excluded).
4. **Service rundown & scenes** — architecture note complete (`ARCHITECTURE.md` section 64), server-side and dashboard UI both implemented. A real new stateful subsystem (verse / media / announcement / blank scenes, stepped through in sequence) with an explicit state machine, not scattered booleans. The precedence question section 59.4 deferred is now resolved: live detection always wins — a live-detected, overridden, or voice-navigated verse always overlays immediately regardless of the rundown's current scene, pausing (not discarding) that scene. Control returns to the paused scene automatically when the interrupting verse is cleared; an explicit operator rundown action (`scene:next`/`previous`/`goto`) during an interrupt always wins instead and discards the pause. New operator-only WS commands (`rundown:load`, `scene:next`, `scene:previous`, `scene:goto`) and a new `rundown:state` broadcast event. The dashboard's "Service Rundown" card lets an operator build a scene list (button-based reorder/remove, not drag-and-drop — see section 64.5) and step through it live. Cross-restart persistence remains explicitly deferred (section 64.5) — a loaded rundown is in-memory only today.
5. **NDI output** — architecture note complete (`ARCHITECTURE.md` section 62), NOT cleared for implementation yet. Raised mid-session as a new broadcast-transport capability alongside the existing OBS Browser Source (not a replacement for it). Reuses the overlay's own existing HTML/CSS/JS, rendered offscreen via Electron's own offscreen-rendering feature rather than a second rendering engine. Needs a native, non-JavaScript dependency (candidate: `grandiose`, wrapping the proprietary NDI SDK) — three things must be verified against its and NDI's real, current terms before any code: SDK licensing/redistribution requirements, prebuilt-binary platform coverage, and package maintenance status (section 62.3). Must degrade gracefully (Browser Source keeps working) if the native module isn't available on a given machine.
6. **AI copilot** — highest risk. Confirmed to mean something broader than the `ReferenceInterpreter` idea below alone (sermon/topic assistance, slide suggestions, a chat-style assistant, the reference-proposal idea, or some combination — not yet decided). Whatever form it takes, any AI-proposed Bible reference must still pass through the same hallucination-guard pipeline `RegexDetector`'s output does today (ARCHITECTURE.md section 15) — never trusted directly. Does not proceed to code before its own dedicated architecture review. **Partially resolved by section 65.7**: sermon-notes summarization specifically (via Groq chat completions, a strictly separate dashboard-only side channel) is approved and scoped — the broader "chat-style assistant"/reference-proposal ideas remain unscoped.
7. **Web-research-driven enhancements** — architecture note complete (`ARCHITECTURE.md` section 65), implemented incrementally, subsection by subsection. Elliptical reference continuation ("verse 16" after "Romans chapter 8"), a trigger-source indicator (detected/override/navigation/rundown), an auto-send vs. review-and-approve mode (auto-send stays default), a voice command to switch display mode, an on-demand glossary lookup by voice, a phone-based second-operator remote (reuses the existing operator token), an AI sermon-notes copilot (section 65.7, see above), and post-service transcript/quote-card export.

## Deferred — not v1, do not implement without an explicit architecture review

Each item below is a candidate future milestone, added as a new implementation behind an existing extension seam (`AsrProvider`, `VerseDetector`, `VerseSource`) wherever possible — not a rewrite.

- **Local / hybrid ASR** (whisper.cpp, Deepgram) — new `AsrProvider` implementation
- **Gemini Live + Google ADK as a `ReferenceInterpreter`** — using Gemini Live's full-duplex streaming understanding to propose a Bible reference directly from speech (instead of transcript + regex). Evaluated and explicitly deferred (not rejected outright): requires real session-management engineering (10-minute forced WebSocket reconnects, resumption tokens, 15-minute context cap without compression) that Groq's stateless per-chunk requests don't need. Its own output would still have to pass through the same hallucination-guard pipeline as any other interpreter — an LLM-proposed reference is never trusted directly, per ARCHITECTURE.md §15. If revisited, build it as an additional `ReferenceInterpreter`/`AsrProvider` implementation alongside Groq/RegexDetector, not a replacement. One candidate building block for Phase 2's AI copilot item above, not the whole of it.
- **Semantic / paraphrase-aware verse detection** — new `VerseDetector` implementation
- **Multiple Bible translations, offline Bible database, vector search** — new `VerseSource` implementations
- Cameras
- Branding engine (as a distinct subsystem — Phase 2's generic-branding first-run step above is a much smaller, already-approved slice of this)
- MCP server
- ProPresenter integration
- Planning Center integration
- Automated OBS control
- Dynamic plugin loading
- Remote / cloud synchronization
- Multi-user networking
- Mobile application
- Cloud backend
